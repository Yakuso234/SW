# SW 秋招面试问题清单

> 用法：先练“短答”，再按追问展开。答案只采用仓库中已有代码、测试、脚本和演示证据；优化项明确说成未来增强。

## 一、项目总览和简历表达

### 1. 你先介绍一下这个项目

SW 是我在开源原项目基础上、经作者允许后重构扩展的短视频微服务平台。我的主线是创作者可靠发布到消费者互动：客户端直传 MinIO，Video Service 用本地事务 Outbox 可靠投递处理任务，Processor 通过 RabbitMQ 驱动 FFmpeg 转码和抽帧，结果回写后发布视频，再通过关注 Feed、点赞、收藏和评论形成消费闭环；同时用 Spring AI 提供权限受控的状态查询和失败诊断。

### 2. 你在项目中主要负责什么

重点回答自己真正做过的重构：视频异步处理状态机、Outbox 和补偿恢复、关注流 Inbox/延迟重试/DLQ、互动消费幂等、Gateway 限流与私有边界、TraceId 和可观测性、AI 工具权限约束，以及测试脚本和故障演练。

### 3. 为什么选择这些技术

Spring Cloud/Nacos/Gateway 负责微服务治理和统一入口；MySQL 保存业务事实和幂等记录；Redis 处理短时状态、Lua 原子操作和限流；RabbitMQ 解耦耗时处理并提供重试/DLQ；MinIO 适合大文件对象存储；FFmpeg 负责媒体处理；Spring AI + SSE 适合流式创作助手。

### 4. 这个项目最能体现你的能力是什么

不是模块数量，而是能把一个跨服务、跨中间件的异步链路讲清楚：失败在哪里发生、状态如何表达、消息如何补偿、重复如何去重、如何监控和复现。

## 二、视频异步处理和 Outbox

### 5. 为什么上传成功后不能直接把视频设为已发布

对象上传成功不代表媒体可解码、可转码、可抽帧，也不代表审核和结果回写成功。只有 Processor 成功产出处理对象并完成条件状态迁移后，视频才进入 `PUBLISHED`。

### 6. 为什么采用预签名直传

大文件不经过业务服务，减少网关和应用服务的带宽、内存和连接占用。业务服务只负责生成受限时效的 URL、记录上传任务和接收提交事件。

### 7. Video、ProcessingTask、Outbox 为什么要拆成三套状态

它们代表三个不同事实：业务视频是否发布、处理任务是否成功、消息是否投递。拆开后可以单独重试和排障，避免把“MQ 已发送”误判成“视频已处理”。

### 8. Outbox 解决了什么问题

业务数据和待发送消息在同一个数据库事务中提交，解决数据库状态与 MQ 消息的双写空窗。提交后由立即发送和定时扫描共同投递，失败记录进入重试或死信状态。

### 9. Outbox 的投递流程是什么

扫描 `PENDING/FAILED` 记录，条件更新抢占为 `SENDING`，发送时带 `x-outbox-id` 和 CorrelationData；Publisher Confirm 成功标记 `SUCCESS`，Confirm 失败或 Return 标记 `FAILED/DEAD`，定时扫描下一次继续补偿。

### 10. 为什么不能说 Outbox 实现了 exactly-once

网络重试、Broker 确认和业务处理之间仍可能出现重复投递。系统采用至少一次投递，靠 eventId、状态条件更新、评论/Inbox 唯一约束等业务幂等手段达到最终正确结果。

### 11. 如果事务提交后应用立刻宕机怎么办

消息仍在 Outbox 表中，重启后的定时扫描会继续发送。立即发送只是降低延迟，不是可靠性的唯一依赖。

### 12. 如果 MQ 不可用怎么办

Outbox 业务记录仍保留，投递器把记录标记为失败并计算下一次重试时间；超过次数进入 `DEAD`，指标和日志记录失败。不能让 HTTP 请求一直同步等待 MQ。

### 13. 为什么 Processor 先 claim 再转码

claim 用 `status = PENDING` 的条件更新抢占任务，保证重复消息不会同时启动多个转码。抢占失败可以安全跳过，因为任务可能已被其他消费者处理或状态已经变化。

### 14. 处理结果回写失败时为什么不直接把视频标记失败

此时 FFmpeg 可能已经成功，失败的是回写链路。若直接标记失败会丢失真实产物；系统保留 `PROCESSING + leaseExpireAt`，租约过期后由 Video Service 创建恢复 Outbox 重新处理。

### 15. 租约和分布式锁有什么区别

租约是持久化的任务拥有权和超时边界，适合跨进程、跨服务的长任务恢复；分布式锁更适合短临界区互斥。视频处理不能只依赖一个可能随进程消失的锁。

### 16. FFmpeg 失败如何处理

捕获异常并截断错误摘要，调用 Video 私有接口把任务置为 `FAILED`、视频置为 `REJECTED`。如果失败结果回写本身不可用，则不丢消息，交给租约恢复。工作目录、临时日志和对象写入也会在 finally/错误路径清理。

## 三、Feed、MQ 和一致性

### 17. 为什么 Feed 使用游标分页而不是 page/offset

深分页需要扫描并跳过大量数据，数据变化时还可能重复或漏数据。系统使用 `publishedAt + id/feedId` 作为稳定排序边界，下一页从游标之后继续读取。

### 18. 关注 Feed 为什么采用 Inbox 扇出

发布时把视频写入关注者 Inbox，读取时只查当前用户的 Feed，读取延迟更稳定。User Service 下游故障不会阻塞视频主发布。代价是粉丝多的创作者会产生大量写入，需要批量、限流和热点策略。

### 19. 关注流消息失败怎么办

先进入带 TTL 的延迟重试队列，最多 3 次，之后进入最终 DLQ。恢复时先写审计和新 Outbox，再 ACK 原 DLQ 消息，不能直接无限 requeue。

### 20. 为什么恢复 DLQ 不直接 requeue

直接 requeue 没有清晰的恢复意图和审计边界，重复操作也难以治理。新 Outbox 可以记录恢复动作、继续使用统一投递器，并在 ACK 前保证恢复意图已持久化。

### 21. Feed 如何防止重复写入

Inbox 通过 `(recipient_id, video_id)` 唯一约束和 `insertIgnoreBatch` 防重；消息重试只会再次尝试写入，不会创建第二条业务记录。

### 22. 高粉丝创作者发布时有什么问题

扇出写放大、User 查询耗时和消息堆积会增加。当前实现分页获取粉丝、分批插入；未来可增加任务调度、限流、混合读写策略、热点创作者读扩散和 Inbox 归档。

## 四、点赞、收藏、评论和幂等

### 23. 点赞为什么先写 Redis

用户关注的是“我是否已经点赞”，这个状态需要低延迟原子切换。Lua 脚本避免并发下先读后写的竞态；缓存未命中时用用户-视频粒度锁回源数据库。

### 24. 点赞数为什么异步更新

状态切换和计数聚合分离可以缩短接口耗时，并把高频计数更新批量化。计数是最终一致，消费端用 eventId 去重，避免 MQ 重投造成重复累加。

### 25. 取消点赞如何避免计数变成负数

当前操作先校验用户状态确实发生变化，事件用 `FRONT/BACK` 表达增减；消费端只处理首次消费的 eventId。生产环境还应通过 SQL 条件和周期性对账进一步保护计数下界。

### 26. 评论为什么使用 Outbox

评论正文不能因为 MQ 暂时不可用而丢失。评论和评论事件在同一事务中落库，消费者用 commentId 幂等后批量更新视频评论数和根评论回复数。

### 27. 点赞/收藏当前是否也使用 Outbox

准确回答：当前用户状态通过 Redis 原子切换后发送 RabbitMQ，消息携带 eventId，Video 消费端写幂等表再批量更新；视频处理、评论计数和关注发布使用 Outbox。后续优化是把点赞/收藏发送也统一纳入 Outbox，以消除状态已变但消息发送失败的窗口。

## 五、Gateway、认证和微服务边界

### 28. Gateway 做了哪些事

统一路由、JWT 解析、把用户 ID 传给下游、WebSocket 握手认证、阻断 `/api/private/` 公网路径，以及用 Redis Lua 做 IP/用户/路由多维滑动窗口限流。

### 29. 多维限流如何保证一致

一次 Lua 脚本同时检查所有维度，任一维度超限就不写入任何计数；全部通过后才对所有 ZSET 添加请求记录。这样不会出现 IP 计数扣了、用户计数没扣的部分成功状态。

### 30. 为什么私有接口还需要阻断

Feign 内部接口是服务协作协议，不应该成为前端可调用 API。Gateway 在路由层直接返回 404，减少暴露面；但这只是边界防护，后续仍应增加服务身份认证。

### 31. JWT 方案有哪些风险和改进点

JWT 适合无状态认证，但撤销、密钥轮换和长期 token 管理需要额外设计。当前项目应继续完善密钥从环境/密钥管理注入、短期 access token + refresh token、密钥轮换和私有调用身份校验。

### 32. User 和 Chat 为什么不因为互关就创建好友

关注是 User 域的社交图谱，聊天会话是 Chat 域的业务对象。互关自动创建聊天会把两个领域强耦合，且会产生隐式副作用；如果产品需要，应由 Chat 域显式创建。

## 六、AI、Agent 和 Python 方向

### 33. 这个项目里的 AI 到底解决什么问题

解决创作者查询处理状态、理解失败摘要和获得标题/简介/标签建议的问题。它不修改视频、不执行发布、不替代状态机，属于受控的业务辅助能力。

### 34. 如何防止模型越权查询别人的视频

模型只提供 videoId，creatorUserId 不从模型参数读取，而是由服务端从用户上下文写入 ToolContext；Video 私有接口再按 `creatorId + videoId` 查询。工具结果没有数据就返回不可访问，不让模型自行猜测。

### 35. 为什么使用 SSE 和 WebFlux

模型回复是流式 token，SSE 可以边生成边返回，降低首字节等待；AI 服务的请求链路适合 WebFlux。阻塞的向量库或外部调用需要放到 boundedElastic 等专用调度器，不能直接阻塞 Reactor 线程。

### 36. AI 工具如何处理模型幻觉

对状态问题强制调用工具，工具结果作为唯一事实来源；失败诊断只允许基于服务端摘要规则匹配，未匹配就明确原因未知；提示词中禁止从 retryCount 等字段推断不存在的事实。

### 37. 这个项目是不是多 Agent

不是当前完成能力。当前是一个 Spring AI 对话服务加两个权限受控的只读工具。`mcp-server` 已有向量记忆、商城检索和用户工具，可以作为后续 MCP/Python Agent 工具层，但不能把代码存在说成多 Agent 业务闭环已经完成。

### 38. 如果继续做 Python Agent，你会如何扩展

先把 Video 状态查询、失败诊断、指标查询、Runbook 操作抽象成带权限和审计的工具协议；再用 Python 做编排层，加入结构化状态机、重试预算、工具超时、人工确认和评测集。先验证单 Agent 的工具选择正确率和越权率，再考虑多 Agent。

## 七、可观测性、测试和故障演练

### 39. TraceId 如何贯穿异步链路

入口读取或生成 `X-Trace-Id`，Feign 透传；创建的消息体记录 TraceId；消费者收到后恢复上下文，再调用 Video Service。日志、指标和脚本输出可以据此串联一次上传。

### 40. 你如何证明项目不是只写了代码

有核心回归测试、成功和失败 E2E 脚本、死信恢复脚本、故障注入参数、Prometheus/Grafana 指标和本地真实联调。面试时展示一条成功链路、一条无效媒体失败链路和一次回写不可用后的恢复链路即可。

### 41. 测试为什么不能只做单元测试

Outbox、RabbitMQ、MinIO、FFmpeg、数据库唯一约束和状态迁移的组合行为，单元测试无法完全覆盖。当前先用单元/服务测试固定状态机和幂等规则，再用本地 E2E 验证真实中间件链路；后续可以把它们纳入 Testcontainers CI。

### 42. 如何解释项目中的性能数据

只能说固定开发机、Docker 中间件、IDEA 服务、串行样本、从预签名请求到 `PUBLISHED/SUCCEEDED/Outbox SUCCESS` 的回归基线。它用于比较改动前后，不代表生产 TPS、并发上限或 SLA。

## 八、反问和优化题

### 43. 如果让你再做一次，最先改什么

第一优先是统一互动事件的可靠投递，把点赞/收藏也纳入 Outbox；第二是补服务间认证；第三是把真实中间件集成测试放入 CI。它们分别补齐可靠性、安全和可交付证据。

### 44. 当前架构最大的规模风险是什么

高粉丝创作者的 Feed 扇出和 FFmpeg 资源消耗。前者需要分批、限流和冷热策略，后者需要并发配额、任务队列和进程资源隔离。

### 45. 你如何判断是否应该继续拆微服务

看业务边界、数据归属、独立扩缩容、故障隔离、团队协作成本和跨服务事务需求，而不是按类或表机械拆分。Video Processor 独立出来是因为 CPU/IO 重、故障边界和扩缩容需求不同；商城等域虽然存在，但当前不纳入核心链路。

### 46. 如果 MQ 消息积压，你会怎么排查

先看队列深度、消费者数量、消费耗时和失败/死信指标；用 TraceId 定位单条消息；再判断是 Processor CPU/FFmpeg、Video 回写、User 粉丝查询还是数据库锁/索引问题。处理上可以临时扩消费者、降低批量或限流，并保留失败消息和重试预算。

### 47. 如果数据库和 Redis 状态不一致怎么办

明确哪个是事实源：用户点赞/收藏关系最终以数据库为准，Redis 是短期状态加速；缓存未命中回源并加锁，必要时通过过期和对账修复。不能把缓存计数直接当作永久事实。

### 48. 如果模型服务超时怎么办

给单次流设置超时和最大消息长度，返回可识别的 SSE 错误事件；工具调用设置 Feign 超时和安全降级；指标记录超时次数，必要时切换备用模型或提示用户稍后重试。不要在超时后编造业务状态。

### 49. 本地 Docker 中间件如何避免和其他项目冲突

Compose 使用独立的 `sw-dev` project name，容器、网络和数据卷由 Compose 自动带上项目维度；环境变量文件只保存本机凭据，并使用独立的 `sw_local` 数据库用户而不是 root。启动命令显式带 `--project-name sw-dev`，避免不同项目的同名服务互相连接或覆盖数据。

### 50. 为什么 Docker 中间件正常但 IDEA 启动的网关仍然 Redis `WRONGPASS`

因为 `.env` 默认由 Docker Compose 读取，不会自动注入到 IDEA 直接启动的 Java 进程。容器使用了 Redis 密码，而网关进程没有继承同一凭据，就会出现端口可达但认证失败。解决方式是把非敏感示例配置与本机凭据分开，并在 IDEA Run Configuration 或用户环境变量中注入同一组凭据；验证时不能只看 TCP 端口，还要做带认证的应用健康检查。

### 51. 为什么前端重构后只保留三个主模块，而不是照搬原前端全部页面

原始前端还包含商城、直播、聊天和商家等存量域，但当前简历主线是可靠视频发布、内容消费互动和受控 AI 助手。重构后的 `SW-web` 只保留能直接演示这三条链路的页面，减少无关依赖和联调成本；前端通过 Gateway 代理服务边界，大文件上传仍走后端返回的 MinIO 预签名 URL。这样面试时可以从一个页面讲清楚业务闭环，而不是罗列没有现场证据的页面数量。

### 52. 前端如何在后端服务暂时未启动时保持可演示

前端请求失败时进入明确标注的 Demo Data 模式，只提供视觉和交互走查，不伪造后端成功结果；真实接口仍通过统一请求层访问 Gateway。登录、互动、投稿和 AI 助手会要求真实身份和服务可用，避免把演示数据误当成真实链路证据。

## 九、最后要背熟的五句话

1. 我把视频业务状态、处理任务状态和消息投递状态拆开，分别表达三类事实。
2. Outbox 解决的是本地数据库与 MQ 的可靠衔接，不是 exactly-once；重复仍靠业务幂等。
3. Processor 回写失败不立即把视频判死，而是依靠处理租约过期和新的 Outbox 补偿。
4. 关注 Feed 的最终死信恢复先落审计和新 Outbox，再 ACK 原消息，保证恢复动作可追踪。
5. AI 在这个项目里是权限受控的只读业务助手；如果继续做 Python Agent，我会先做工具边界、状态机、审计和评测，再扩展多 Agent。
