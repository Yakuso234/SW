## 一、项目总览和简历表达

### 1. 你先介绍一下这个项目

SW 是我在开源原项目基础上、经作者允许后重构扩展的短视频微服务平台。我的主线是创作者可靠发布到消费者互动：客户端直传 MinIO，Video Service 用本地事务 Outbox 可靠投递处理任务，Processor 通过 RabbitMQ 驱动 FFmpeg 转码和抽帧，结果回写后发布视频，再通过关注 Feed、点赞、收藏和评论形成消费闭环；同时用 Spring AI 提供权限受控的状态查询和失败诊断。

### 2. 你在项目中主要负责什么

重点回答自己真正做过的重构：视频异步处理状态机、Outbox 和补偿恢复、关注流 Inbox/延迟重试/DLQ、互动消费幂等、Gateway 限流与私有边界、TraceId 和可观测性、AI 工具权限约束，以及测试脚本和故障演练。

### 3. 为什么选择这些技术

Spring Cloud/Nacos/Gateway 负责微服务治理和统一入口；MySQL 保存业务事实和幂等记录；Redis 处理短时状态、Lua 原子操作和限流；RabbitMQ 解耦耗时处理并提供重试/DLQ；MinIO 适合大文件对象存储；FFmpeg 负责媒体处理；Spring AI + SSE 适合流式创作助手。

### 4. 这个项目最能体现你的能力是什么

不是模块数量，而是能把一个跨服务、跨中间件的异步链路讲清楚：失败在哪里发生、状态如何表达、消息如何补偿、重复如何去重、如何监控和复现。

## 二、视频异步处理和 Outbox

### 5. 为什么上传成功后不能直接把视频设为已发布

对象上传成功不代表媒体可解码、可转码、可抽帧，也不代表审核和结果回写成功。只有 Processor 成功产出处理对象并完成条件状态迁移后，视频才进入 `PUBLISHED`。

### 6. 为什么采用预签名直传

大文件不经过业务服务，减少网关和应用服务的带宽、内存和连接占用。业务服务只负责生成受限时效的 URL、记录上传任务和接收提交事件。

### 7. Video、ProcessingTask、Outbox 为什么要拆成三套状态

它们代表三个不同事实：业务视频是否发布、处理任务是否成功、消息是否投递。拆开后可以单独重试和排障，避免把“MQ 已发送”误判成“视频已处理”。

### 8. Outbox 解决了什么问题

业务数据和待发送消息在同一个数据库事务中提交，解决数据库状态与 MQ 消息的双写空窗。提交后由立即发送和定时扫描共同投递，失败记录进入重试或死信状态。

### 9. Outbox 的投递流程是什么

扫描 `PENDING/FAILED` 记录，条件更新抢占为 `SENDING`，发送时带 `x-outbox-id` 和 CorrelationData；Publisher Confirm 成功标记 `SUCCESS`，Confirm 失败或 Return 标记 `FAILED/DEAD`，定时扫描下一次继续补偿。

### 10. 为什么不能说 Outbox 实现了 exactly-once

网络重试、Broker 确认和业务处理之间仍可能出现重复投递。系统采用至少一次投递，靠 eventId、状态条件更新、评论/Inbox 唯一约束等业务幂等手段达到最终正确结果。

### 11. 如果事务提交后应用立刻宕机怎么办

消息仍在 Outbox 表中，重启后的定时扫描会继续发送。立即发送只是降低延迟，不是可靠性的唯一依赖。

### 12. 如果 MQ 不可用怎么办

Outbox 业务记录仍保留，投递器把记录标记为失败并计算下一次重试时间；超过次数进入 `DEAD`，指标和日志记录失败。不能让 HTTP 请求一直同步等待 MQ。

### 13. 为什么 Processor 先 claim 再转码

claim 用 `status = PENDING` 的条件更新抢占任务，保证重复消息不会同时启动多个转码。抢占失败可以安全跳过，因为任务可能已被其他消费者处理或状态已经变化。

### 14. 处理结果回写失败时为什么不直接把视频标记失败

此时 FFmpeg 可能已经成功，失败的是回写链路。若直接标记失败会丢失真实产物；系统保留 `PROCESSING + leaseExpireAt`，租约过期后由 Video Service 创建恢复 Outbox 重新处理。

### 15. 租约和分布式锁有什么区别

租约是持久化的任务拥有权和超时边界，适合跨进程、跨服务的长任务恢复；分布式锁更适合短临界区互斥。视频处理不能只依赖一个可能随进程消失的锁。

### 16. FFmpeg 失败如何处理

捕获异常并截断错误摘要，调用 Video 私有接口把任务置为 `FAILED`、视频置为 `REJECTED`。如果失败结果回写本身不可用，则不丢消息，交给租约恢复。工作目录、临时日志和对象写入也会在 finally/错误路径清理。

## 三、Feed、MQ 和一致性

### 17. 为什么 Feed 使用游标分页而不是 page/offset

深分页需要扫描并跳过大量数据，数据变化时还可能重复或漏数据。系统使用 `publishedAt + id/feedId` 作为稳定排序边界，下一页从游标之后继续读取。

### 18. 关注 Feed 为什么采用 Inbox 扇出

发布时把视频写入关注者 Inbox，读取时只查当前用户的 Feed，读取延迟更稳定。User Service 下游故障不会阻塞视频主发布。代价是粉丝多的创作者会产生大量写入，需要批量、限流和热点策略。

### 19. 关注流消息失败怎么办

先进入带 TTL 的延迟重试队列，最多 3 次，之后进入最终 DLQ。恢复时先写审计和新 Outbox，再 ACK 原 DLQ 消息，不能直接无限 requeue。

### 20. 为什么恢复 DLQ 不直接 requeue

直接 requeue 没有清晰的恢复意图和审计边界，重复操作也难以治理。新 Outbox 可以记录恢复动作、继续使用统一投递器，并在 ACK 前保证恢复意图已持久化。

### 21. Feed 如何防止重复写入

Inbox 通过 `(recipient_id, video_id)` 唯一约束和 `insertIgnoreBatch` 防重；消息重试只会再次尝试写入，不会创建第二条业务记录。

### 22. 高粉丝创作者发布时有什么问题

扇出写放大、User 查询耗时和消息堆积会增加。当前实现分页获取粉丝、分批插入；未来可增加任务调度、限流、混合读写策略、热点创作者读扩散和 Inbox 归档。

## 四、点赞、收藏、评论和幂等

### 23. 点赞为什么先写 Redis

用户关注的是“我是否已经点赞”，这个状态需要低延迟原子切换。Lua 脚本避免并发下先读后写的竞态；缓存未命中时用用户-视频粒度锁回源数据库。

### 24. 点赞数为什么异步更新

状态切换和计数聚合分离可以缩短接口耗时，并把高频计数更新批量化。计数是最终一致，消费端用 eventId 去重，避免 MQ 重投造成重复累加。

### 25. 取消点赞如何避免计数变成负数

当前操作先校验用户状态确实发生变化，事件用 `FRONT/BACK` 表达增减；消费端只处理首次消费的 eventId。生产环境还应通过 SQL 条件和周期性对账进一步保护计数下界。

### 26. 评论为什么使用 Outbox

评论正文不能因为 MQ 暂时不可用而丢失。评论和评论事件在同一事务中落库，消费者用 commentId 幂等后批量更新视频评论数和根评论回复数。

### 27. 点赞/收藏当前是否也使用 Outbox

准确回答：当前用户状态通过 Redis 原子切换后发送 RabbitMQ，消息携带 eventId，Video 消费端写幂等表再批量更新；视频处理、评论计数和关注发布使用 Outbox。后续优化是把点赞/收藏发送也统一纳入 Outbox，以消除状态已变但消息发送失败的窗口。

## 五、Gateway、认证和微服务边界

### 28. Gateway 做了哪些事

统一路由、JWT 解析、把用户 ID 传给下游、WebSocket 握手认证、阻断 `/api/private/` 公网路径，以及用 Redis Lua 做 IP/用户/路由多维滑动窗口限流。

### 29. 多维限流如何保证一致

一次 Lua 脚本同时检查所有维度，任一维度超限就不写入任何计数；全部通过后才对所有 ZSET 添加请求记录。这样不会出现 IP 计数扣了、用户计数没扣的部分成功状态。

### 30. 为什么私有接口还需要阻断

Feign 内部接口是服务协作协议，不应该成为前端可调用 API。Gateway 在路由层直接返回 404，减少暴露面；但这只是边界防护，后续仍应增加服务身份认证。

### 31. JWT 方案有哪些风险和改进点

JWT 适合无状态认证，但撤销、密钥轮换和长期 token 管理需要额外设计。当前项目应继续完善密钥从环境/密钥管理注入、短期 access token + refresh token、密钥轮换和私有调用身份校验。

### 32. 为什么关注关系不自动创建额外社交业务对象

关注是 User 域的社交图谱，互关不应隐式创建好友、会话等其他业务对象，否则会引入跨域强耦合和难以追踪的副作用；如果后续产品需要，应由新业务域显式发起创建。当前仓库已主动移除不属于短视频主线的聊天等存量模块。

## 六、AI、Agent 和 Python 方向

### 33. 这个项目里的 AI 到底解决什么问题

解决创作者查询处理状态、理解失败摘要和获得标题/简介/标签建议的问题。它不修改视频、不执行发布、不替代状态机，属于受控的业务辅助能力。

### 34. 如何防止模型越权查询别人的视频

模型只提供 videoId，creatorUserId 不从模型参数读取，而是由服务端从用户上下文写入 ToolContext；Video 私有接口再按 `creatorId + videoId` 查询。工具结果没有数据就返回不可访问，不让模型自行猜测。

### 35. 为什么使用 SSE 和 WebFlux

模型回复是流式 token，SSE 可以边生成边返回，降低首字节等待；AI 服务的请求链路适合 WebFlux。阻塞的向量库或外部调用需要放到 boundedElastic 等专用调度器，不能直接阻塞 Reactor 线程。

### 36. AI 工具如何处理模型幻觉

对状态问题强制调用工具，工具结果作为唯一事实来源；失败诊断只允许基于服务端摘要规则匹配，未匹配就明确原因未知；提示词中禁止从 retryCount 等字段推断不存在的事实。

### 37. 这个项目是不是多 Agent

不是。SW 中的 AI 是一个 Spring AI 对话服务加权限受控的只读工具，重点仍是微服务可靠性。真正的 Python Agent 项目是独立的 DG/FlowPilot；两者只通过过期视频任务恢复场景完成过一次受控集成，不能因此把 SW 描述成多 Agent 平台。

### 38. 如果继续做 Python Agent，你会如何扩展

我已经在独立的 DG/FlowPilot 中实现这条路线：用 Python、FastAPI 和 LangGraph 编排调查、提案、风险复核、人工审批和受控执行，模型只生成结构化建议，服务端负责权限、状态机、幂等和审计。SW 只提供受限业务接口；真实联调已验证 DG 审批后触发过期任务恢复，SW 最终推进到 `PUBLISHED / SUCCEEDED`。两套项目保持独立，避免把 Agent 编排逻辑塞进视频服务。

## 七、可观测性、测试和故障演练

### 39. TraceId 如何贯穿异步链路

入口读取或生成 `X-Trace-Id`，Feign 透传；创建的消息体记录 TraceId；消费者收到后恢复上下文，再调用 Video Service。日志、指标和脚本输出可以据此串联一次上传。

### 40. 你如何证明项目不是只写了代码

有核心回归测试、成功和失败 E2E 脚本、死信恢复脚本、故障注入参数、Prometheus/Grafana 指标和本地真实联调。面试时展示一条成功链路、一条无效媒体失败链路和一次回写不可用后的恢复链路即可。

### 41. 测试为什么不能只做单元测试

Outbox、RabbitMQ、MinIO、FFmpeg、数据库唯一约束和状态迁移的组合行为，单元测试无法完全覆盖。当前先用单元/服务测试固定状态机和幂等规则，再用本地 E2E 验证真实中间件链路；后续可以把它们纳入 Testcontainers CI。

### 42. 如何解释项目中的性能数据

只能说固定开发机、Docker 中间件、IDEA 服务、串行样本、从预签名请求到 `PUBLISHED/SUCCEEDED/Outbox SUCCESS` 的回归基线。它用于比较改动前后，不代表生产 TPS、并发上限或 SLA。

## 八、反问和优化题

### 43. 如果让你再做一次，最先改什么

第一优先是统一互动事件的可靠投递，把点赞/收藏也纳入 Outbox；第二是补服务间认证；第三是把真实中间件集成测试放入 CI。它们分别补齐可靠性、安全和可交付证据。

### 44. 当前架构最大的规模风险是什么

高粉丝创作者的 Feed 扇出和 FFmpeg 资源消耗。前者需要分批、限流和冷热策略，后者需要并发配额、任务队列和进程资源隔离。

### 45. 你如何判断是否应该继续拆微服务

看业务边界、数据归属、独立扩缩容、故障隔离、团队协作成本和跨服务事务需求，而不是按类或表机械拆分。Video Processor 独立出来是因为 CPU/IO 重、故障边界和扩缩容需求不同；商城等域虽然存在，但当前不纳入核心链路。

### 46. 如果 MQ 消息积压，你会怎么排查

先看队列深度、消费者数量、消费耗时和失败/死信指标；用 TraceId 定位单条消息；再判断是 Processor CPU/FFmpeg、Video 回写、User 粉丝查询还是数据库锁/索引问题。处理上可以临时扩消费者、降低批量或限流，并保留失败消息和重试预算。

### 47. 如果数据库和 Redis 状态不一致怎么办

明确哪个是事实源：用户点赞/收藏关系最终以数据库为准，Redis 是短期状态加速；缓存未命中回源并加锁，必要时通过过期和对账修复。不能把缓存计数直接当作永久事实。

### 48. 如果模型服务超时怎么办

给单次流设置超时和最大消息长度，返回可识别的 SSE 错误事件；工具调用设置 Feign 超时和安全降级；指标记录超时次数，必要时切换备用模型或提示用户稍后重试。不要在超时后编造业务状态。

### 49. 本地 Docker 中间件如何避免和其他项目冲突

Compose 使用独立的 `sw-dev` project name，容器、网络和数据卷由 Compose 自动带上项目维度；环境变量文件只保存本机凭据，并使用独立的 `sw_local` 数据库用户而不是 root。启动命令显式带 `--project-name sw-dev`，避免不同项目的同名服务互相连接或覆盖数据。

### 50. 为什么 Docker 中间件正常但 IDEA 启动的网关仍然 Redis `WRONGPASS`

因为 `.env` 默认由 Docker Compose 读取，不会自动注入到 IDEA 直接启动的 Java 进程。容器使用了 Redis 密码，而网关进程没有继承同一凭据，就会出现端口可达但认证失败。解决方式是把非敏感示例配置与本机凭据分开，并在 IDEA Run Configuration 或用户环境变量中注入同一组凭据；验证时不能只看 TCP 端口，还要做带认证的应用健康检查。

### 51. 为什么前端重构后只保留三个主模块，而不是照搬原前端全部页面

原始前端还包含商城、直播、聊天和商家等存量域，但当前简历主线是可靠视频发布、内容消费互动和受控 AI 助手。重构后的 `SW-web` 只保留能直接演示这三条链路的页面，减少无关依赖和联调成本；前端通过 Gateway 代理服务边界，大文件上传仍走后端返回的 MinIO 预签名 URL。这样面试时可以从一个页面讲清楚业务闭环，而不是罗列没有现场证据的页面数量。

### 52. 前端如何在后端服务暂时未启动时保持可演示

前端请求失败时进入明确标注的 Demo Data 模式，只提供视觉和交互走查，不伪造后端成功结果；真实接口仍通过统一请求层访问 Gateway。登录、互动、投稿和 AI 助手会要求真实身份和服务可用，避免把演示数据误当成真实链路证据。

### 53. 为什么 AI 文档写了 Key，但服务仍可能启动失败或前端一直报不可用

密钥名和运行拓扑必须形成同一份契约。本次重装后发现文档约定 `QWEN_API_KEY`，AI/MCP 的 Nacos 配置却读取 `OPENAI_API_KEY`；AI 服务还默认连接 Nacos `8848`、Redis `6379`，与 SW 隔离后的 `28848/16379` 不一致。结果可能是 Key 明明已配置却无法创建模型客户端，或服务连接到错误项目的中间件。修复方式是统一使用 `QWEN_API_KEY`，所有宿主机连接统一复用 `SW_*` 端口变量，并重新导入 Nacos 配置。这个问题说明配置项命名、密钥注入和 Compose 隔离不仅是运维细节，也是微服务可复现性的组成部分。

### 54. IDEA 本地配置已被 Git 忽略，为什么排障时仍要防止密钥泄露

Git 忽略只能防止文件进入版本库，不能防止密钥出现在本地 `workspace.xml`、终端输出、截图、录屏或诊断日志中。IDEA Run Configuration 的环境变量可能以明文写入本地工作区文件，因此排障脚本只能输出变量名和是否存在，不能直接打印配置文件或变量值；一旦密钥进入聊天或日志，应立即在供应商控制台撤销并轮换，而不是只删除本地文本。更稳妥的长期方案是使用系统密钥存储或专用 Secret Manager，并让应用在运行时按权限读取。

### 55. 为什么 Spring Redis 已配置 localhost，Redisson 仍然尝试解析 redis

项目同时使用 Spring Data Redis 和 Redisson，它们读取的是两套配置键：`spring.data.redis.*` 与 `redisson.address`。只修正前者并不能改变 Redisson；存量 Nacos 配置中的 `redis://redis:6379` 是 Compose 容器网络地址，IDEA 宿主机无法解析。修复时必须沿 Bean 创建异常追到 `RedissonConfig` 的实际绑定属性，再把 Redisson 地址也统一为 `redis://${SW_REDIS_HOST:localhost}:${SW_REDIS_PORT:16379}`。这说明排障不能看到“Redis 配置正确”就停止，还要确认失败组件究竟消费了哪组配置。

### 56. Video Service 已健康且 Feed 接口返回 200，为什么前端仍然刷不到视频

服务可用性、接口成功和业务数据就绪是三件事。本次现场检查确认 Gateway 与 Video 的 `/public/feed` 均返回 200，但本机 `video` 表为空；Feed SQL 又明确过滤 `status=5(PUBLISHED)` 和 `published_at IS NOT NULL`，因此返回空 `items` 是正确业务结果。要产生真实 Feed 数据，必须完成预签名上传、MinIO 落盘、Outbox/MQ、Processor/FFmpeg 转码和发布回写；仅启动 Video Service 不会自动生成视频。前端应把“后端不可达”和“后端可达但没有已发布数据”做成不同空状态，Demo 数据也必须明确标注，不能掩盖数据链路尚未完成。

### 57. 服务都正常，为什么首次上传仍然报 MinIO `NoSuchBucket`

对象存储进程健康只说明 MinIO 可访问，不代表业务 Bucket 已初始化。新的隔离数据卷不会自动拥有 `video`、`user` Bucket，因此预签名 PUT 会在真正上传时失败。本地启动脚本通过 MinIO Client 幂等创建这两个私有 Bucket；Bucket 不开放匿名读，播放由后端生成短期预签名 GET URL。现场证据是完整 E2E 达到 `PUBLISHED / SUCCEEDED / Outbox SUCCESS`，Feed 返回签名地址，媒体 Range 请求返回 HTTP 206。

### 58. 为什么一条用户资料缺失的评论会让整个评论列表失败

评论列表是 Video 评论数据与 User 用户资料的跨服务聚合。原实现假设每个评论用户都能查到资料，直接解引用姓名和头像；测试数据、注销用户或跨服务数据不一致时，一个缺失用户就会触发空指针并破坏整页。修复后评论正文仍以 Video 数据为事实，缺失资料降级为“已注销用户”；回复中的发送方和接收方也分别容错。该问题说明聚合接口必须允许部分数据缺失，不能把装饰性用户资料当作评论可见性的前置条件。

### 59. 为什么新注册用户的评论写入成功，回读却报 S3 `Key must not be null`

新用户默认没有头像对象 Key，但用户聚合代码仍无条件调用预签名 GET，AWS SDK 在构造请求时拒绝 null Key。修复放在公共 `AWSUtils.generateAccessUrl` 边界：null 或空白 Key 原样返回 null，真实 Key 才生成签名 URL，因此 Profile、关注列表、搜索和评论聚合都共享同一防线。单元测试固定空 Key 行为，真实 JWT 联调进一步验证注册、登录、点赞、收藏、评论和评论回读全部成功。

### 60. 为什么前端还要做登录门禁，后端 Public Feed 不是公开接口吗

接口公开性和产品页面访问策略是两层设计。后端保留 Public Feed 便于内容分发和未来游客模式；当前秋招演示产品要求先建立身份，再显示 Feed、Creator 和 AI 页面，避免用户进入后才发现大部分操作需要登录。前端门禁不替代 Gateway JWT 鉴权，真正受保护的互动、投稿和 AI 接口仍由后端校验。浏览器验证确认未登录时无主导航，登录后显示真实 Feed，退出后重新隐藏业务页面。

### 61. 如何证明“关注后创作者发布的视频会推到我的关注流”不是只写了接口

使用独立 E2E 脚本创建临时创作者和关注者，关注者先调用关注接口；创作者走预签名上传、提交、Outbox、RabbitMQ、FFmpeg 和发布回写。脚本随后以关注者 JWT 轮询 `/video/api/me/follow-feed`，必须命中新视频并断言 `isFollowed=true`。2026-08-23 现场结果中 `FollowFeedContainsPublishedVideo=True`，说明验证覆盖了社交关系、异步发布、Inbox 扇出与消费侧读取，而不只是 Controller 返回 200。这里的“推流”指短视频关注内容扇出，不等同于 RTMP 实时推流；后者不在当前收敛后的仓库范围内。

### 62. 播放量为什么要做每日去重，如何避免前端显示与后端不一致

新增 `video_view_event`，用 `(video_id, viewer_id, viewed_date)` 唯一约束作为最终去重边界。播放请求先 `insert ignore` 事件，只有插入成功才递增 `video.views`，并向前端返回布尔值：第一次 `true`、重复播放 `false`。前端不再无条件乐观加一，只在 `true` 时刷新当前卡片计数。单测覆盖新事件和重复事件两个分支；真实 E2E 对同一用户连续请求两次，断言 `FirstViewCounted=True`、`SecondViewDeduplicated=True`、创作者总观看 `1`，同时返回补零的 7 天趋势。口径仅适合本地演示，生产仍需完播阈值、反刷量、匿名/设备策略和离线分析。

### 63. 创作者运营页面为什么不自己在前端算统计数据

作品数、点赞、评论、收藏和观看来自 Video 服务聚合，粉丝/关注来自 User 服务，前端只展示后端事实并提供资料修改、作品删除、收藏读取等受限 CRUD。这样数据归属仍在领域服务，前端不会把当前页 Feed 或 Demo Data 当成全量统计；页面还明确显示观看口径，避免演示图表被误解为生产 BI。浏览器验证了视频/创作者搜索、7 根趋势柱和收藏从异步写入后的空状态变为 1 条，控制台无错误。

### 64. 为什么外部恢复编排联调会被业务自动恢复“抢跑”，如何让验证可重复

过期租约的定时扫描与人工恢复接口使用同一条 `PROCESSING + lease_expire_at <= now` 状态条件。直接插入一条过期测试任务时，Video 的定时扫描会先把任务恢复为 `PENDING` 并投递 Outbox，Processor 随后可能先消费；如果测试源对象不存在，最终就会变为 `REJECTED / FAILED`，但这并不证明外部编排器执行了恢复。为此增加默认开启的 `sw.video-processing.automatic-recovery-enabled`：仅本地演练时设为 `false`，暂停定时扫描而不影响私有人工恢复接口。这样可稳定验证“恢复前状态 → 外部编排器触发 → 新 Outbox → Processor 后续处理”；测试源还必须使用真实可读对象，不能用不存在的 Key。该开关不应作为生产常态配置。

现场验证中，DG 对隔离任务 `7321572775443310` 完成真实调查、LangGraph 提案、HITL 审批和受控恢复，SW 返回恢复成功；随后 Processor 将任务推进到 `SUCCEEDED/retryCount=1`、视频推进到 `PUBLISHED`，恢复与发布 Outbox 都成功。重复执行复用 DG 的同一 ExecutionRecord、attempts 仍为 1。这个案例适合说明：异步联调不仅要断言最终成功，还要控制竞争者、保证测试资源真实，并用跨系统状态和审计证据证明到底是谁触发了动作。

## 记录 065：Redis 秒杀库存丢失后如何安全重建

### 背景

秒杀请求先由 Redis Lua 原子校验活动时间、库存和用户资格，再在 MySQL 事务中创建待支付订单。Redis 承担高并发入口削峰，但订单和销量事实仍在 MySQL。

### 问题 / 风险

待支付订单已经预扣 Redis 库存，却还没有进入 `sold_count`。如果 Redis 重启后只用 `total_stock - sold_count` 重建，这部分预占会被错误释放，后续请求可能超卖；同时如果不恢复买家集合，同一用户会反复穿透到数据库唯一约束。

### 最终方案

活动缓存按 `总库存 - 已支付销量 - 待支付订单数` 重建，并从该活动的订单表恢复已参加用户集合。Redis 负责快速拒绝，MySQL 的订单唯一约束继续作为最终并发兜底。

### 关键不变量 / 论证

- `sold_count` 只表达已支付销量，不能代表全部占用。
- `PENDING_PAYMENT` 订单必须继续占库存。
- Redis 可以丢失和重建，MySQL 才是订单事实源。
- 任何缓存重建都不能让可售库存大于数据库事实推导出的上限。

### 验证证据

Java 21 聚合编译通过；`VideoCommerceServiceImplTest` 覆盖售罄映射、事务回滚补偿和提交后取消回补。真实本地 E2E 使用 12 个隔离买家并发争抢 3 件库存，最终 3 单成功、9 单拒绝，MySQL 订单数为 3、Redis 剩余库存为 0、未超卖；该批请求在当前开发机约 60.91 ms。此结果是固定小场景功能回归，不是生产压测或 TPS 结论。

### 边界 / 代价

当前重建会查询单个活动订单，适合本地演示和中小数据量。生产规模应增加单活动初始化锁、版本号、分批恢复和定期对账，并避免多个实例并发覆盖活动缓存。

### 面试表达

“Redis 只是秒杀入口门闩，不是库存事实源。我重建库存时没有只减已支付销量，而是同时扣除待支付预占，并恢复买家集合；这样 Redis 丢失后不会把未付款订单占用的库存重新卖一遍，数据库唯一约束再做最终兜底。”

## 记录 066：为什么事务回滚和订单取消必须使用不同的库存补偿

### 背景

Lua 预扣发生在 MySQL 下单事务之前。预扣之后既可能因为数据库异常导致事务回滚，也可能在订单成功落库后由用户取消或定时任务关单。

### 问题 / 风险

如果两种情况都“库存加一并删除用户资格”，会与数据库的活动买家唯一约束冲突；如果取消时在事务提交前就修改 Redis，数据库随后回滚却会留下虚增库存，形成超卖窗口。

### 最终方案

拆成两类 Lua 补偿：下单事务回滚时释放用户资格并回补库存，使没有订单记录的用户可以重试；取消或超时订单只回补库存并保留用户资格，而且通过事务同步在 `afterCommit` 后执行。

### 关键不变量 / 论证

- 没有持久化订单时，预扣必须完整撤销。
- 已持久化订单时，买家资格语义必须与数据库唯一约束一致。
- 外部缓存补偿不能先于本地数据库事务提交。
- 条件更新订单状态失败时，不允许重复回补库存。

### 验证证据

两套脚本、事务同步和条件更新已进入代码并通过 Java 21 编译。3 项定向单测验证：数据库事务回滚时执行 release，取消只有在事务提交后执行 restock，且取消不会从买家集合删除用户；完整接口 E2E 还验证了下单、模拟支付、发货、收货和退款审核的状态迁移。

### 边界 / 代价

Redis 回补发生在提交后，若提交成功后 Redis 短暂不可用，需要后续对账或补偿任务修复；当前版本还没有建立独立库存补偿 Outbox，因此不能声称实现了生产级最终一致性。

### 面试表达

“我没有把所有库存回补都写成一个脚本。事务回滚表示订单不存在，要恢复库存和用户资格；取消或超时表示订单事实已经存在，只在数据库提交后回补库存。这样缓存补偿、唯一约束和业务幂等的语义是一致的。”

## 记录 067：为什么个性化记忆采用 Redis、MySQL、Milvus 三层结构

### 背景

创作者助手需要记住用户的受众、标题风格、选题和内容约束，但这是秋招演示项目，既要有真实个性化，也要控制 Embedding 调用、向量存储和提示词长度成本。

### 问题 / 风险

把全部聊天自动向量化会制造大量低价值记忆、增加成本，还可能把过时内容和提示注入长期保存；只存聊天历史又无法支持用户查看、纠正和删除，也不能稳定检索跨会话偏好。

### 最终方案

Redis 保存限制轮数和 TTL 的最近会话；MySQL 只保存用户主动确认的长期偏好，并提供列表、保存和软删除；Milvus 作为可重建向量索引，以 `user_id` 过滤召回。处理进度、转码失败等事实问题绕过偏好召回，Milvus或 Embedding 失败时回退到 MySQL 最近偏好。

### 关键不变量 / 论证

- MySQL 是长期记忆事实源，Milvus 不是。
- 只有当前用户能检索和删除自己的记忆。
- 用户输入和记忆只作为不可信上下文，不能覆盖系统规则或工具权限。
- 事实查询以业务工具结果为准，个性化偏好不能改写状态事实。
- 当前不自动抽取、不重排，用更少调用换取成本和可解释性。

### 验证证据

记忆 CRUD、短期会话、向量索引与降级代码已完成，AI 模块 Java 21 编译和 5 项定向单测通过；真实 `sw-dev` Milvus 集成测试完成固定 768 维向量的写入、按用户隔离检索和删除。接口 E2E 验证 MySQL 记忆保存、列表与软删除；浏览器验证登录后记忆管理面板正常渲染且控制台无错误。当前机器没有可供命令行进程使用的 `QWEN_API_KEY`，因此本轮没有把真实 Qwen Embedding 调用记为通过，只验证了模型调用失败时回退 MySQL 的路径。

### 边界 / 代价

没有自动记忆抽取、冲突合并、时间衰减、重排和离线召回评测；软删除后向量删除是尽力而为，生产环境应补异步索引任务、删除对账和效果数据集。

### 面试表达

“我把记忆按生命周期和事实性拆成三层：Redis 管最近会话，MySQL 管用户可见可删的长期偏好，Milvus 只做可重建的语义索引。事实型问题绕过个性化召回，向量服务失败就回退 MySQL；这样在较低成本下保证了个性化、可控删除和权限边界。”

## 记录 068：为什么 R2DBC 保存带业务 ID 的新实体会被误判为更新

### 背景

创作者长期记忆使用 Snowflake ID，由应用在写入前生成；AI 服务的数据访问使用 Spring Data R2DBC。首次真实接口 E2E 中，内存 ID 已生成，但数据库里还没有对应记录。

### 问题 / 风险

直接调用 `repository.save(entity)` 时，R2DBC 会根据实体 ID 判断它是否为新对象。非空 Snowflake ID 让框架选择 `UPDATE`，最终因数据库中不存在该行而报出 `Row with Id ... does not exist`。如果只看 DTO、Controller 或 Mock 测试，这个差异不会暴露；更危险的是把失败误判成数据库连接问题或 ID 冲突。

### 最终方案

为新增长期记忆定义显式 `INSERT` 查询，调用方在生成 Snowflake ID 后走 `insertMemory(...)`；列表、软删除等更新路径继续使用 Repository 查询。这样“由应用生成主键”与“数据库操作语义”被明确拆开，不再依赖框架的新实体推断。

### 关键不变量 / 论证

- 非空 ID 不等价于数据库中已经存在该记录。
- 新增与更新语义必须由持久化操作明确表达，不能只依赖实体状态猜测。
- MySQL 插入成功才表示长期记忆事实成立；Milvus 索引失败不能反向抹掉这条事实。
- 该修复不能用把 ID 改成数据库自增来规避，因为项目跨模块统一使用 Snowflake ID，改变主键策略会扩大影响面。

### 验证证据

修复前真实 HTTP E2E 稳定复现 `Row with Id does not exist`；改为显式 INSERT 后，同一路径完成保存、列表命中、软删除和删除后不可见。`CreatorMemoryServiceImplTest` 还验证向量索引异常时 MySQL 保存仍然成功。

### 边界 / 代价

显式 SQL 会降低一部分 Repository 自动化便利，字段新增时必须同步修改 INSERT 语句；但新增语义更清晰，也更适合对业务 ID、软删除和审计字段做稳定控制。

### 面试表达

“我在真实联调里发现，R2DBC 的 `save` 会把带非空 Snowflake ID 的新实体当成更新。我的修复不是改主键策略，而是把新增写成显式 INSERT，让业务 ID 生成和数据库存在性彻底解耦；这也提醒我，ORM 的 `save` 不是天然的 upsert。”

## 记录 069：为什么 Milvus 集合主键字段必须与 SDK 写入合同完全一致

### 背景

长期记忆以 MySQL 为事实源，Milvus 保存 768 维向量索引。开发阶段先完成了接口和失败降级，随后用真实 `sw-dev` Milvus 做独立集成测试。

### 问题 / 风险

Milvus Java SDK 的快速建表默认要求主键字段为 `id`，最初代码写入的 JSON 字段却是 `memory_id`，因此服务返回 `field id not provided`。Mock 向量存储或只验证降级路径会让该问题长期隐藏；如果误以为 MySQL CRUD 通过就代表向量召回完成，会在简历和面试中夸大证据。

### 最终方案

显式声明集合主键名为 `id`，写入文档同步使用 `id`，检索结果从 SDK 返回的主键读取业务记忆 ID；`user_id` 继续作为过滤字段，向量维度与 Qwen Embedding 配置统一为 768。增加带开关的真实 Milvus 集成测试，测试结束删除专用集合。

### 关键不变量 / 论证

- 集合 Schema、插入 JSON、检索结果解析必须共享同一字段合同。
- 所有向量检索必须包含当前 `user_id` 过滤，不能只靠相似度后置筛选。
- Milvus 中的主键对应 MySQL 记忆 ID，便于回表并过滤已软删除记录。
- 向量索引是可重建派生数据，索引不可用时不能影响 MySQL 事实写入。

### 验证证据

真实集成测试先复现 `field id not provided`，修复后在项目隔离的 Milvus 上完成固定 768 维向量写入、当前用户命中、其他用户隔离和删除后不可召回，1/1 通过并清理测试集合。由于本轮命令行环境没有真实 Qwen Key，证据只覆盖 Milvus 合同，不宣称真实模型 Embedding 请求已验证。

### 边界 / 代价

当前集合使用轻量快速 Schema，尚未做索引参数调优、召回率数据集、时间衰减或重排评测；生产化还需要异步索引 Outbox、失败重试和 MySQL—Milvus 删除对账。

### 面试表达

“向量库接入的难点不只是把文本转成向量，Schema 合同和隔离边界同样重要。我用真实 Milvus 测试发现 SDK 默认主键是 `id`，而写入使用了 `memory_id`；修复后用写入、用户隔离检索和删除三段断言证明链路，而不是拿 MySQL CRUD 成功冒充 RAG 已完成。”

## 记录 070：为什么单元测试不能依赖数据库第一行和服务发现

### 背景

本轮新增功能定向测试和 E2E 已通过，但重跑 Video/AI 历史全量套件时仍有两个旧测试失败：状态测试直接取 `video` 表第一行，评论测试启动完整 Spring 上下文后通过 Feign 查 User Service。

### 问题 / 风险

数据库第一行会随故障演练、E2E 和插入顺序变化，测试却假定它处于 `PROCESSING`；评论测试名义上验证本地逻辑，实际要求 Nacos 中存在可调用的 `userService`。这类用例在某一台机器上偶然成功，却无法区分业务回归、测试数据漂移和外部依赖未启动，既拖慢反馈，也会让开发者习惯性忽略红灯。

### 最终方案

把两项测试收敛为确定性的 Controller 委托单测：使用 Mock Service 验证参数和调用关系，不启动 Spring、不读取本地库、不经过服务发现。视频合法状态迁移由已有 `VideoServiceImplTest` 覆盖；评论写 Outbox和用户资料缺失降级由已有 `InteractionServiceImplTest` 覆盖；真实跨服务行为仍交给隔离账号 E2E。

### 关键不变量 / 论证

- 单元测试输入必须由测试自己创建或 Mock，不能依赖共享开发库的自然顺序。
- Controller 委托、Service 业务规则和跨服务 E2E 应分层取证，不能用一个重型上下文测试同时承担三种职责。
- 外部服务未启动不应让纯本地委托测试失败；真正需要外部服务的测试必须显式标记和准备依赖。
- 修测试不能删除业务断言：被移出的状态迁移、Outbox 和降级语义都要在对应 Service 测试中有替代证据。

### 验证证据

修复前全量套件稳定出现 `expected PUBLISHED but was REJECTED` 和 `UnknownHostException: userService`；改造后 Video 全量 44/44 通过，AI 常规套件通过，真实 Milvus 集成测试另以环境开关运行 1/1 通过。

### 边界 / 代价

Controller Mock 测试不能证明 MyBatis 映射、Nacos 或 Feign 网络合同，因此仍需要独立集成测试和真实 E2E。当前部分历史 `@SpringBootTest` 仍较重，后续可继续按测试金字塔拆分，但本轮没有为了追求数量改写全部上游测试。

### 面试表达

“全量回归里有两个红灯并不是业务失败，而是测试分别依赖数据库第一行和未启动的 User Service。我没有直接跳过它们，而是把 Controller 委托、Service 规则和跨服务 E2E 分层：委托用 Mock，状态机和 Outbox 用 Service 单测，真实链路用隔离 E2E。改造后 Video 44 项全绿，失败信号也更可信。”

## 九、最后要背熟的五句话

1. 我把视频业务状态、处理任务状态和消息投递状态拆开，分别表达三类事实。
2. Outbox 解决的是本地数据库与 MQ 的可靠衔接，不是 exactly-once；重复仍靠业务幂等。
3. Processor 回写失败不立即把视频判死，而是依靠处理租约过期和新的 Outbox 补偿。
4. 关注 Feed 的最终死信恢复先落审计和新 Outbox，再 ACK 原消息，保证恢复动作可追踪。
5. AI 在这个项目里是权限受控的只读业务助手；如果继续做 Python Agent，我会先做工具边界、状态机、审计和评测，再扩展多 Agent。
